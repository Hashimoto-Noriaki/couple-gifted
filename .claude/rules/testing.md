# テスト

## TDD

- **backendのみ**。Specを先に書いてから実装する
- **frontendはTDDの対象外**。UIは変更が激しく、テストを先に書いても画面の作り直しのたびに書き直しになるため。
  テストは実装の後に、下記「対象範囲の考え方」のロジック（hooks・整形ロジック・認証まわり等）に絞って書く

### 基本サイクル

TDDの手順の正本はここ。`CLAUDE.md`等の他ファイルは「Specを先に書いてから実装する」の1行に留め、詳細はここを参照する。

0. **テストリスト**：確かめたいケースを先に箇条書きにする（例：評価あり／評価なし／0件／次ページあり）。
   1つ選んで以下のサイクルを回し、リストが空になるまで繰り返す。途中で思いついたケースはリストに足す
1. **Red**：失敗するテストを書き、**実行して、期待した理由で失敗することを確認する**
   - 「メソッドが無い」「期待値と違う」など、狙い通りの理由で落ちているかを見る。タイポや設定ミスで落ちているなら、それはRedではない
   - 一度も失敗を見ていないテストは、壊れた実装でも通ってしまう（何も検証していない）可能性がある。
     AIに実装させるときも、テストと実装を同時に書かせず、失敗を確認してから実装に進ませる
2. **Green**：テストを通す**最小限**のコードを書く。きれいさより、まず通すことを優先する
3. **Refactor**：テストが通る状態を保ったまま、実装とテストコードを整える（重複の除去・命名の改善など）。
   整えたら再度テストを実行し、通ることを確認する

## カバレッジ

- 目標は**C1（分岐カバレッジ）**。backend/frontend共通、モノレポ全体の方針
- 数値目標（◯%以上等）はまだ決めない。実コードとテストがある程度増えてから、CIゲートにするかどうかも含めて判断する
- **backend**：SimpleCovは未導入（Gemfileに無し）。導入時は`SimpleCov.enable_coverage :branch`で分岐カバレッジを有効化する（Ruby 3.4系で対応済み）
- **frontend**：既存のVitestにcoverage（v8 provider）を追加するとき、分岐カバレッジを計測する設定にする

## 対象範囲の考え方

- **backend**：TDDの原則通り、モデル・コントローラは基本的に全部テストする。このプロジェクトのドメインルールは「if分岐そのものが仕様」のケースが多い（サプライズは返さない、招待コードは理由を問わず同じエラー、招待コード発行済みなら弾く等）。C0（行カバレッジ）だと分岐の片側だけ通してもカバレッジ上は満点になり得るが、C1ならドメインルールの両方の枝を通す必要があるため相性がよい
- **frontend**：UIは変更が激しく、全部を単体テストで網羅するとメンテナンスコストが見合わない。優先してテストするのは以下：
  - hooks（ロジックの塊）
  - Server Componentのレンダリング（データ取得結果が正しく反映されているか）
  - 表示用にデータを整形する純粋なロジック（日付・予算帯のフォーマット等）
  - 認証まわり
  - 見た目だけのプレゼンテーション的なコンポーネントは、Vitestでの網羅よりStorybookでの確認を優先する（役割分担）

## Rails APIのモック（frontend）

- Vitestのユニットテストで、実際のRails APIに到達しない（モックする）
- 具体的な手段（Vitest標準の`vi.mock()`か、MSWのようなネットワークレベルの傍受か）はまだ決めない。Rails APIを呼ぶコードの置き場所（境界層）が決まってから選ぶ。今MSWを追加するのは時期尚早（TanStack Queryと同じ理由）

## E2E

- **backend**：Request Specが実質E2E相当（ルーティング〜コントローラ〜モデルを通しで検証する）。追加のE2Eツールは不要
- **frontend**：今は未導入。導入するときも全ユーザー導線を網羅しない。**認証（サインアップ・ログイン・ログアウト）に絞る**
  - 理由：認証は壊れると他の機能が一切使えなくなる基盤で、かつ一度実装すれば変化が少ない。UIが変化しやすい機能フローにE2Eを張るとメンテナンスコストが見合わない
  - ツール（Playwright等）は未定。最初の縦串（認証が動く状態）ができてから選ぶ

## ファイル配置

- **backend**：RSpecの慣習通り、`spec/`が`app/`を鏡写しする（コロケーションしない）
- **frontend**：コロケーション。`.spec.tsx`を対象ファイルと同じ階層に置く（詳細は`.claude/rules/frontend.md`参照）
