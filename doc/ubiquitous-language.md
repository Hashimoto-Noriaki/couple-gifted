# 用語の統一（ユビキタス言語）

- **最終更新**：2026-07-31
- **対象**：`docs/requirements.md`、`docs/user-stories.md`、`docs/use-cases.md`
- **本書の目的**：同じ言葉が場所によって別の意味で使われていないかを点検し、統一する

> **重要：本書は一括置換の対象外とする。**
> 本書には「使わないと決めた言葉」が例として載っているため、置換すると内容が壊れる。
> エディタの複数ファイル置換では、必ず本書を除外すること。

---

## この作業の位置づけ

大事なのはこれだけ。

> **同じ言葉を、全員が同じ意味で使えているか？**

「なんとなく通じている」で進めると、後から「それってそういう意味だったの？」が必ず起きる。
設計に入る前に一度点検する。**新しい用語を覚える作業ではなく、自分が書いた文書を読み直す作業。**

### やり方

1. 要件定義・ユーザーストーリー・ユースケースを読み返す
2. 同じ言葉なのに、使う場所によって意味が変わっていないかを探す
3. 見つけたら「この言葉はこの意味で統一する」と決める
4. 決めたことを残す

今回は3ドキュメントを横断して用例を機械的に収集し、多義的に使われている語を特定した。

---

## 気づき①：「共有」が3つの意味で使われている

**もっとも影響が大きい揺れ。** 実際の用例を並べると3つに分かれていた。

| 用例 | 意味 |
| --- | --- |
| 「二人で共有」か「サプライズ」を選ぶ | 保存リストの**可視性の設定値** |
| カップルとして書いた「共有レビュー」 | レビューが**カップルに紐づいている**こと |
| 記録を二人で「共有」したいから | **カップル連携そのもの** |

3つは仕組みがまったく違う。特に「共有保存リスト」と「共有レビュー」は、同じ「共有」という語を使っているが、前者は可視性の話、後者は帰属の話であり、実装も別になる。

### どう決めたか（「共有」）

**「共有」は保存リストの可視性を指す語としてのみ使う。**

| 言いたいこと | 使う言葉 |
| --- | --- |
| 保存リストがパートナーに見える状態 | 共有 |
| 保存リストが本人にしか見えない状態 | サプライズ |
| レビューがカップルに紐づいている | **カップルレビュー** |
| レビューが個人に紐づいている（未連携時） | **ソロレビュー** |
| パートナーとつながっている状態 | **連携** |

「共有レビュー」「共有記録」「共有データ」という語は**使わない**。

## 気づき②：「解除」が2つの意味で使われている

| 用例 | 意味 |
| --- | --- |
| パートナーとの連携を「解除」する | 関係の終了。不可逆 |
| 絞り込みを「解除」して全件表示に切り替える | 検索条件のクリア。何度でも戻せる |

一方は取り返しがつかない操作、もう一方は気軽な操作。同じ語を使うのは危険。
特に画面上で「解除」というラベルが2つの意味で現れると、誤操作を招く。

### どう決めたか（「解除」）

**「解除」は連携の終了にのみ使う。**

| 言いたいこと | 使う言葉 |
| --- | --- |
| カップル連携を終わらせる | **連携解除** |
| 検索条件を外す | **絞り込みを外す** / **すべて表示** |

あわせて「カップル解除」という表記も使わない。解除されるのは連携であり、カップルという存在そのものではない。**連携解除**に統一する。

## 気づき③：「子どもの有無」が2つの意味で使われている

これは**要件そのものの誤りを含んでいた。**

| 用例 | 意味 |
| --- | --- |
| プロフィールに「子どもの有無」を登録する | 子どもが**いるかどうか**（人の属性） |
| 「子連れで行けるかどうかで選べる場所が変わる」 | そのとき子どもを**連れて行くかどうか**（訪問のしかた） |

この2つは同じではない。**子どもがいる夫婦が、子どもを預けて二人で出かけることは頻繁にある。**
検索やレビューの絞り込みで本当に必要なのは後者であって、前者ではない。

### どう決めたか（「子どもの有無」）

2つの別の概念として分離する。

| 概念 | 言葉 | 置く場所 |
| --- | --- | --- |
| 子どもがいるかどうか | **子どもの有無** | プロフィール（初期値の補完に使う） |
| そのとき子どもを連れて行ったか | **子連れ訪問** | レビューの属性・検索の絞り込み軸 |

絞り込みの軸は「子連れ訪問」に変更する。「子どもの有無」は初期値を補完するためだけに使う。

## 気づき④：「予算帯」の単位が定義されていなかった

「予算帯」は9箇所に登場するが、**ひとりあたりなのか、ふたり合計なのかがどこにも書かれていない。**

レビューを投稿する人と読む人で解釈が食い違えば、この属性は機能しない。

### どう決めたか（「予算帯」）

**ふたり合計・税込**とする。

理由は、本サービスの記録の単位が「二人で行った体験」であるため。「二人で1万円だった」という言い方の方が、投稿する側の実感に近い。

グルメサイトは通常ひとりあたりで表示するため、既存サービスに慣れた利用者は誤解する可能性がある。**画面上に必ず「ふたり合計」と明示する。**

## 気づき⑤：「交際初期」と「交際中」が意味的に重なっている

関係ステージの定義で、「交際初期」と「交際中」を並列のステージとして置いていた。

しかし**交際初期も日本語としては「交際中」である。** 並列に置くと、どちらに入るのか判断できない。

### どう決めたか（「交際初期」「交際中」）

傘となる語とステージ名を分ける。

| 種別 | 言葉 |
| --- | --- |
| 傘（交際している状態全般） | **交際期** |
| ステージ名 | **交際初期**（6ヶ月未満） / **交際中期**（6ヶ月以上） |

**「交際中」は日常語として意味が広すぎるため、ステージ名には使わない。**
文中で交際している状態全般を指したいときは「交際期」を使う。

## 気づき⑥：「カップル」が2つの意味で使われている

| 用例 | 意味 |
| --- | --- |
| 「カップル・夫婦向けのライフプラットフォーム」 | 交際している二人（夫婦と対比されている＝未婚） |
| 「カップルメンバー」「カップルレビュー」 | 連携した二人1組の単位（夫婦を含む） |

「カップル・夫婦向け」と並列に書くと、カップルは未婚を指すことになる。
一方でアクター名の「カップルメンバー」には夫婦も含まれる。定義が衝突している。

### どう決めたか（「カップル」）

**ドキュメント内の用語としての「カップル」は、連携した二人1組を指す。婚姻状態は問わない。**

サービスの紹介文で対象者を説明するときは、「カップル」と「夫婦」を並列にしない。
「交際中から結婚後までのふたり」のように書く。

## 気づき⑦：「記録」と「レビュー」

ユーザーストーリーでは「記録を残したい」、要件定義とユースケースでは「レビューを投稿する」と書かれていた。同じものを指している。

### どう決めたか（「記録」「レビュー」）

ドキュメント上の用語は**「レビュー」に統一**する。ただし利用者に見せる言葉としては「記録」を使ってよい。この2つは対応関係にある。

**ここから派生した論点**：「記録」という言葉を使ったとき、利用者は必ずしも公開を前提にしていない。
インタビューでも「良かった場所を後から探せない」という記録欲求が挙がっている。
**公開しないレビュー（自分たちだけの記録）を許すかどうかが未定義だった。** 未決事項に追加する。

## 決まった言葉一覧

| 言葉 | 意味 | 使わない言葉 |
| --- | --- | --- |
| **カップル** | 連携した二人1組の単位。婚姻状態を問わない | ー |
| **連携** | 招待コードによってカップルが成立している状態 | 共有（この意味では） |
| **連携解除** | 連携を終了させること。不可逆 | カップル解除、解除（単体） |
| **共有** | 保存リストがパートナーから見える状態 | ー |
| **サプライズ** | 保存リストが本人にしか見えない状態 | 非公開、プライベート |
| **カップルレビュー** | カップルに紐づくレビュー | 共有レビュー、共有記録 |
| **ソロレビュー** | 個人に紐づくレビュー（未連携時に投稿） | ー |
| **レビュー** | 評価・属性・本文からなる投稿の全体 | 記録（ドキュメント上では） |
| **評価** | 5段階の点数のみを指す | ー |
| **交際期** | 交際している状態全般（傘となる語） | 交際中 |
| **交際初期 / 交際中期** | 関係ステージの名称 | 交際中、付き合いたて |
| **関係ステージ** | 交際初期・交際中期・婚約中・新婚・夫婦の区分 | ステージ（単体での略記） |
| **子どもの有無** | 子どもがいるかどうか。プロフィールの属性 | ー |
| **子連れ訪問** | そのとき子どもを連れて行ったか。レビューの属性・検索軸 | 子どもの有無（この意味では） |
| **予算帯** | **ふたり合計・税込**の金額の区分 | ー |
| **絞り込みを外す** | 検索条件をクリアすること | 解除 |
| **スポット** | 掲載単位となる場所。マスタのレコードを指す | 店舗、お店 |
| **招待コード** | 連携のために発行する文字列。常に1つだけ有効 | 招待（単体） |

## まだ定義されていない言葉

**ER図・DB設計に入る前に**、選択肢を確定させる必要がある。
列挙型かマスタテーブルになるため物理設計の入力になるが、概念モデルの形は変えないので、ドメイン設計の段階では未定義のまま進めてよい。

| 言葉 | 未定義な点 |
| --- | --- |
| **シーン** | 選択肢が列挙されていない（記念日／日常／初デート／両家対応 等） |
| **エリア** | 粒度が未定義（都道府県／市区町村／沿線／エリア名） |
| **好みのタグ** | 選択肢を運営が定義するのか、自由入力なのか |
| **カテゴリ** | スポットの分類軸が未定義 |
| **予算帯の区分** | 何円刻みで区切るのか |

## 反映作業の手順

対象は `requirements.md`、`user-stories.md`、`use-cases.md` の3ファイル。**本書は対象外。**

### 一括置換してよいもの

| 置換前 | 置換後 | 件数 |
| --- | --- | --- |
| `カップル解除` | `連携解除` | requirements 3 |
| `絞り込みを解除` | `絞り込みを外す` | use-cases 1 |
| `付き合いたて` | `交際初期` | requirements 5 |

`付き合いたて` のうち、インタビュー表の行ラベル2箇所はステージ名なので必須。
残り3箇所は文章中なので、読みやすさを優先して言い換えてもよい。

### 正規表現が必要なもの

```bash
交際中(?!期)   →   交際中期
```

requirements の3箇所が対象。`(?!期)` を付けないと、2回実行したときに「交際中期期」になる。

### 手動で判断するもの

**`共有` で始まる複合語は、例外なく手動。**
「共有」は可視性を指す正式な用語であるため、続く語との組み合わせが「可視性の話か、帰属の話か」を毎回判断する必要がある。機械的には決まらない。

| 対象 | 修正内容 |
| --- | --- |
| `共有レビュー`（requirements 1） | 対になる行と合わせて `ソロレビュー` / `カップルレビュー` に書き換える |
| `共有記録`（use-cases 1） | `カップルレビューと共有保存リスト` に開く。保存リストが落ちないよう注意 |
| `共有データ`（3ファイル計4） | 文脈に応じて `カップルレビューと共有保存リスト` に開く |
| `共有していた`（3ファイル計4） | 同上 |
| `共有保存リスト` | **正しい用法。変更しない** |
| `子どもの有無`（計10のうち3） | レビューの属性・検索の絞り込み軸として書かれた3箇所のみ `子連れ訪問` に変更。プロフィール属性の7箇所はそのまま |
| `記録`（退会ユースケース周辺） | `レビュー` に統一 |
| `カップル・夫婦向け`（requirements 2） | `交際中から結婚後までのふたり向け` に書き換え |

### 置換ではなく書き足すもの

- 予算帯の単位（ふたり合計・税込）を機能要件に明記
- 未決事項に「公開しないレビューを許すか」を追加
- 決定事項ログに用語統一の決定を追加

## この作業で分かったこと

用語の点検は言い換えの作業ではなかった。**要件の誤りが2件見つかった。**

- 絞り込みの軸が「子どもがいるか」になっていたが、必要なのは「子どもを連れて行ったか」だった
- 「予算帯」の単位が定義されておらず、そのままでは属性として機能しなかった

どちらも設計を書き始めてから気づくと、テーブル定義とAPIの修正が必要になっていた。
**言葉を点検する作業は、設計の前に置くべき工程である。**

### 反映作業から分かったこと

用語集そのものを一括置換の対象に含めてしまい、内容が壊れた。
**用語集は「使わないと決めた言葉」を保持する文書であるため、置換対象から除外しなければならない。**
同じ理由で、今後 ADR を書く場合も置換対象から外す。過去の判断を記録した文書は、当時の言葉のまま保つ必要がある。
