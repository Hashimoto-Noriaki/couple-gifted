## このサービスのドメイン

**「ふたりで出かける場所を決めて、記録し、次に活かす世界」。**

この世界の特徴は、**同じ人でも関係の段階によって「良い場所」が変わる**ことにある。
交際初期に良かった店が、子どもが生まれた後には使えない。だから評価は「誰が」だけでなく「どの段階のふたりが」に紐づく。

もうひとつの特徴は、**同じデータでも相手に見せてよいものと見せてはいけないものがある**こと。
パートナーは他人ではないが、すべてを共有する相手でもない。サプライズはこの世界に固有の要求である。

## STEP1. 対象物（モノ）の一覧

| 対象物 | 何を表すか |
| --- | --- |
| **会員** | サービスを使う個人。交際開始日・結婚日を持つ |
| **カップル** | 連携したふたり1組。関係の器 |
| **招待コード** | 連携を成立させるための鍵 |
| **スポット** | 掲載される場所。運営が登録する |
| **レビュー** | ある訪問についての評価と記録 |
| **保存** | 行きたい場所の控え。共有かサプライズかを持つ |
| **通報** | 不適切な投稿の申告 |
| **記念日** | 本人が任意で登録する日付。意味は本人が決める |
| **診断** | 質問への回答と、そこから導いた提案 |
| **管理操作の記録** | 誰がいつ何を削除・停止したか |

## STEP2. 対象物＋動詞＋ルール

### 会員

- 会員は、登録できる。ただし、ニックネームが空の場合はできない。
- 会員は、登録できる。ただし、利用規約に同意していない場合はできない。
- 会員は、**関係ステージを自分で選べる。** 交際初期・交際中期・婚約中・新婚・夫婦のいずれか。
- 会員は、関係ステージを選ばないままでもよい。その場合は「未設定」となる。
- 会員は、退会できる。ただし、自分が書いたレビューの扱いを選ばない限りできない。
- 会員は、退会できる。ただし、パスワードを再入力しない限りできない。
- 会員は、パートナーと連携していなくても、レビューを書ける。

**重要な設計判断1**：関係ステージは、**カップルではなく会員が持つ**。
ソロの会員でもステージが決まり、レビューが絞り込みとランキングの対象になるようにするため。

**重要な設計判断2**：**交際開始日・婚約日・結婚日を収集しない。**
ステージ判定に日付は不要であり、日付は本人にとって重い情報になり得る。
日付が必要になるのは記念日リマインドという付加機能だけなので、そこは任意登録の「記念日」で受け止める。
付加機能のために全員から日付を集めることは、「収集する情報は最小限に限る」という方針と矛盾する。

### 関係ステージ

会員が選ぶ。日付からの算出は行わない。

| ステージ | 選ぶ目安 |
| --- | --- |
| 交際初期 | 交際して間もない |
| 交際中期 | 交際が続いている |
| 婚約中 | 婚約から結婚まで |
| 新婚 | 結婚して間もない |
| 夫婦 | 結婚生活が続いている |
| 未設定 | 選んでいない |

- ステージは、いつでも変更できる。
- ステージが未設定の会員のレビューは、ステージ別の絞り込みとランキングの対象にしない。
- 連携している場合、ふたりの選択が食い違うことがある。**そのときは差分を提示して揃えてもらう。システムが勝手に選ばない。**
- ステージは**自動では変わらない。** 婚約・結婚・出産は本人が意識する変化であるため、本人の操作で更新する。

### カップル

- カップルは、成立できる。ただし、双方が他の相手と連携していない場合に限る。
- カップルは、解除できる。ただし、**片方の意思のみで解除できる。** 相手の承認を必要としない。
- カップルは、解除できる。ただし、取り消すことはできない。
- カップルは、解除できる。ただし、解除前に何がどうなるかを提示しない限りできない。
- カップルは、解除したとき、**関係ステージを選び直すよう本人に促す。**
  その関係は終わっているため、放置すると実態と合わないステージのままになる。
- 同じ相手と、解除後に再度連携できる。
- 一方が退会した場合、連携は解除された状態として扱う。

### 招待コード

- 招待コードは、発行できる。ただし、既にパートナーと連携している場合はできない。
- 招待コードは、発行できる。ただし、**有効なコードは1会員につき常に1つだけ。** 再発行すると前のコードは無効になる。
- 招待コードは、発行できる。ただし、短時間に繰り返し発行することはできない。
- 招待コードは、7日を過ぎると使えない。
- 招待コードは、1回の連携成立で使い切りとなる。
- 招待コードは、使える。ただし、自分が発行したものは使えない。
- 招待コードは、使える。ただし、発行者が既に別の相手と連携している場合は使えない。
- 招待コードは、使える。ただし、発行者が退会・停止している場合は使えない。
- 招待コードは、使える。ただし、入力に連続して失敗すると一時的に使えなくなる。
- **使えない理由は、区別して伝えない。** 区別すると、コードが存在するかどうかを外部から判定できてしまうため。
- 招待コードには、**拒否という操作が存在しない。** 使わなければ期限切れで終わる。

### スポット

- スポットは、運営だけが登録・編集できる。
- スポットは、登録できる。ただし、同名・同一位置のものが既にある場合は警告する。
- スポットは、**削除できない。** レビューが投稿されている場合は、非掲載に切り替える。
- スポットは、ゲストでも検索・閲覧できる。

### レビュー

- レビューは、投稿できる。ただし、評価が未選択の場合はできない。
- レビューは、投稿できる。ただし、本文が文字数の上限を超える場合はできない。
- レビューは、投稿できる。ただし、写真がサイズ・形式・枚数の条件を満たさない場合はできない。
- レビューは、**投稿した時点の関係ステージを保持する。** 後からステージが変わっても、書き換わらない。
- レビューは、**同じスポットに何度でも投稿できる。** 再訪して評価が変わることは、この世界では正常な出来事である。
- ただし、**スポットの平均評価に数えるのは、1組につき1スポットあたり最新の1件だけ。** 同じ組が何度書いても平均は偏らない。
- レビューは、下書きとして保存できる。ただし、下書きはパートナーからも見えない。
- レビューは、**公開しない状態で完成させることはできない**（第1フェーズ）。記録だけしたい場合は下書きに留める。
- レビューは、編集・削除できる。ただし、書いた本人と管理者だけができる。
- レビューは、予算帯を持つ。**予算帯はふたり合計・税込**である。
- レビューは、子連れ訪問かどうかを持つ。これは会員の「子どもの有無」とは別の情報である。

### 保存

- 保存は、共有かサプライズかを選んでできる。
- 保存は、共有としてできる。ただし、パートナーと連携していない場合はできない。
- 保存は、サプライズとしてできる。**連携していなくてもできる。**
- 保存は、同じスポットを共有とサプライズの両方に持てる。**ただし、本人にだけ警告を出す。**
  禁止しない理由：禁止すると共有側から先に外す必要が生じ、**その削除がパートナーに見えてしまう。**
  サプライズを守るための制約が、サプライズを壊す。
- 保存は、同じモードの中で重複できない。
- 保存は、サプライズから共有に変更できる。ただし、パートナーに見えるようになることを警告した後に限る。
- 保存は、**共有からサプライズに戻せない。** 既に見られた可能性を取り消せないため。

### 通報

- 通報は、できる。ただし、自分の投稿にはできない。
- 通報は、できる。ただし、同じ投稿に二重にはできない。
- 通報は、**投稿者に伝わらない。**
- 通報は、対応できる。ただし、管理者だけができる。
- 通報は、対応できる。ただし、対応理由を入力しない限りできない。

### 記念日

- 記念日は、**任意で登録できる。** 登録しなくてもサービスの中心機能は使える。
- 記念日は、複数登録できる。交際記念日と結婚記念日の両方を持ちたい要求があるため。
- 記念日は、**意味を本人が決められる。** 交際開始でも結婚でも、初デートでもよい。
- 記念日は、パートナーと連携している場合、共有される。
- 記念日は、関係ステージの判定には使わない。
- 記念日は、削除できる。

※ 記念日リマインドは Should 項目のため、第1フェーズでは登録と表示までとする。

### 診断

- 診断は、回答を保存できる。途中で離脱しても、次回は続きから再開できる。
- 診断は、提案できる。ただし、**理由を説明できない提案はしない。**
- 診断は、提案できる。ただし、該当がない場合は条件を緩めた提案を出す。

### 管理操作の記録

- 削除・停止は、**必ず記録される。** 実行者・日時・対応内容・理由を残す。
- 管理操作は、実行できる。ただし、確認を経ない限りできない。

## STEP3. 見え方のルール（この世界に固有のもの）

対象物ごとのルールとは別に、**誰から見えるか**が横断的なルールとして存在する。

| データ | 本人 | パートナー | 他の会員 | 管理者 |
| --- | :---: | :---: | :---: | :---: |
| 公開済みレビュー | ○ | ○ | ○ | ○ |
| 下書きレビュー | ○ | × | × | ○ |
| 保存（共有） | ○ | ○ | × | ○ |
| 保存（サプライズ） | ○ | × | × | ○ |
| 交際開始日・結婚日 | ○ | ○ | × | ○ |
| メールアドレス | ○ | × | × | ○ |

**サプライズについては、「見えない」の意味を厳密に定める。**

- 一覧に出ない
- 詳細を開けない
- 検索結果に出ない
- **件数にも数えられない**
- **保存されているスポットの表示が、パートナー側で他と変わらない**
- **保存が存在すること自体が伝わらない**

一度でも漏れれば、この機能は二度と使われない。**「見えないこと」を確認するテストを持つ。**

## STEP4. 独立した"モノ"として扱うかどうかの判断

判断基準は同じ。

> 「一覧で確認したい」「後から状態を参照したい」という要件があるか？

### 独立した"モノ"にしたもの

| 対象物 | 理由 |
| --- | --- |
| 招待コード | 有効・期限切れ・使用済みという**状態を発行者が確認したい**という要件がある |
| 保存 | 一覧で見たい。かつ共有かサプライズかという状態を持つ |
| 通報 | 管理者が未対応の一覧を見たい。対応履歴も残したい |
| 記念日 | 一覧で見たい。複数持てる。ステージとは独立して増減する |
| 診断 | 途中から再開したい。次回の初期値にも使いたい |
| 管理操作の記録 | 誰がいつ何をしたかを後から参照したい（監査性の要件） |
| カップル | 連携中か解除済みかという状態を持ち、レビューの帰属先にもなる |

### 独立した"モノ"にしなかったもの

| 概念 | 理由 |
| --- | --- |
| **関係ステージ** | 会員が持つ属性のひとつ。選択肢の集合であり、状態や履歴を持たない |
| **下書き** | レビューの状態のひとつ。別の対象物にすると、公開時に移し替えが必要になる |
| **訪問** | レビューが訪問日を持てば足りる。同一スポットへの複数投稿を許すため、レビュー自体が訪問の記録になる |
| **予算帯・シーン・カテゴリ・エリア** | レビューやスポットが持つ属性。選択肢の管理方法は ER図・DB設計で決める |
| **子どもの有無** | 会員が持つ属性。**子連れ訪問**はレビューが持つ属性。どちらも独立した対象物ではない |

## STEP5. 技術の都合で歪めてはいけない判断

**ここに挙げた3つは、一見すると冗長・不親切に見えるが意図的である。**
リファクタリングや「改善」の対象にしてはならない。変更する場合は、要件定義書の決定事項ログを確認すること。

### 1. レビューは、投稿時点の関係ステージを保持する

会員の日付から算出できるので、一見すると重複データに見える。
しかし**算出し直すと、過去のレビューまで現在のステージに書き換わる。** 交際初期に書いた評価が、結婚後には「夫婦の評価」になってしまう。

**このサービスの価値そのものが失われるため、重複して保持する。**

### 2. 保存は、持ち主と連携の両方に紐づく

共有の保存はカップルのもの、サプライズの保存は本人のもの。
片方だけに紐づけると、サプライズがパートナーから見えるか、共有が成立しないかのどちらかになる。

### 3. 招待コードの使えない理由を区別しない

利用者から見ると不親切に見える。
しかし理由を区別すると、**コードが存在するかどうかを外部から判定できてしまう。** 総当たりの手がかりになる。

## STEP6. ドメイン設計で新たに判明した論点

| # | 論点 | 内容 |
| --- | --- | --- |
| 1 | 平均評価の「最新の1件」の判定基準 | 投稿日時か訪問日か。再訪の記録という性質上、訪問日が妥当と考えられるが未確定 |
| 2 | ふたりのステージ選択が食い違ったときの扱い | 差分を提示して揃えてもらう方針としたが、揃えるまでのステージをどう扱うかは未定 |
| 3 | ステージが長期間更新されない場合の扱い | 実態とずれ続ける可能性がある。確認を促す仕組みは第2フェーズで検討 |
| 4 | 記念日をパートナーに共有する範囲 | 連携時に既存の記念日を自動で共有するか、選ばせるか |

### 解消した論点

**婚約日の欠落**：日付を収集しない方式に変更したため消滅した。
当初は「関係ステージに婚約中があるのに、交際開始日と結婚日からは算出できない」という矛盾があった。
ステージを直接選ぶ方式では、そもそも算出しないため問題にならない。

## この後の工程との関係

本書で決めた対象物・動詞・ルールを、それぞれの技術の形に翻訳していく。

| 工程 | 翻訳するもの |
| --- | --- |
| 画面遷移図・ワイヤーフレーム | 動詞を、どの画面のどの操作にするか |
