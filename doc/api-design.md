## APIって何？（レストランの例え）

APIとは、**「注文の窓口」**。

- **お客さん（画面）**が「これください」と注文する
- **店員（API）**が、厨房に注文を伝える
- **厨房（データベース）**が料理を用意する
- **料理（データ）**がお客さんに返ってくる

大事なのは、**お客さんは厨房の中を知らなくていい**こと。
画面は、データベースの中の仕組みを知らなくていい。窓口に「このデータください」「これを保存して」と頼めば、結果が返ってくる。

この「頼み方のルール」を決めるのがAPI設計。

---

## API設計＝ドメインの「動詞」を窓口にする

新しく考えることはほとんどない。ドメイン設計で決めた**動詞**が、そのまま窓口になる。

「レビューを投稿する」という動詞は、「レビューを投稿する窓口」というAPIになる。

---

## 窓口の一覧

### 会員・認証

| やりたいこと（動詞） | 窓口の役割 |
| --- | --- |
| 新規登録する | 会員を新しく作る |
| ログインする | 本人か確認して、入れるようにする |
| ログアウトする | 出る |
| 自分の情報を見る | ニックネーム・ステージ・連携状態をまとめてもらう |
| プロフィールを編集する | 自分の情報を書き換える |
| 関係ステージを選ぶ | 自分のステージを設定・変更する |
| 退会する | アカウントを消す。レビューの扱いを選ぶ |

### カップル連携

| やりたいこと | 窓口の役割 |
| --- | --- |
| 招待コードを発行する | 自分のコードを作る（前のコードは無効になる） |
| 招待コードの状態を見る | 有効か、残り何日かをもらう |
| 招待コードを入力する | コードを渡して連携を成立させる |
| 連携を解除する | 関係を終わらせる |

### 記念日

| やりたいこと | 窓口の役割 |
| --- | --- |
| 記念日を登録する | 名前と日付を追加する |
| 記念日の一覧を見る | 自分たちの記念日をもらう |
| 記念日を削除する | 1件消す |

### スポットを探す

| やりたいこと | 窓口の役割 |
| --- | --- |
| スポットを検索する | 条件に合うスポットの一覧をもらう |
| スポットの詳細を見る | スポット1つの詳しい情報をもらう |
| レビューを読む | そのスポットのレビュー一覧をもらう（絞り込み可） |
| ランキングを見る | ステージ別・エリア別の並びをもらう |

### レビュー

| やりたいこと | 窓口の役割 |
| --- | --- |
| レビューを投稿する | 評価と属性を記録する |
| 下書きを保存する | 公開せずに残す |
| レビューを編集する | 自分の投稿を書き換える |
| レビューを削除する | 自分の投稿を消す |
| 自分のレビューを見る | 公開済みと下書きの一覧をもらう |

### 保存

| やりたいこと | 窓口の役割 |
| --- | --- |
| スポットを保存する | 共有かサプライズかを選んで記録する |
| 保存リストを見る | 共有／サプライズの一覧をもらう |
| サプライズを共有に変える | 可視性を切り替える |
| 保存を外す | 1件消す |

### 診断

| やりたいこと | 窓口の役割 |
| --- | --- |
| 診断に答える | 回答を記録する（途中でもよい） |
| 提案をもらう | 回答に合うスポットと、選んだ理由をもらう |

### 安全

| やりたいこと | 窓口の役割 |
| --- | --- |
| 投稿を通報する | 不適切な投稿を運営に知らせる |

### 管理者

**管理者向けの窓口は作らない。**

管理画面はRails側に持ち、APIを経由しないと決めた（決定事項ログ #30・#31）。
APIファーストはクライアントとサーバの契約に関する方針であり、サーバ内部の運営ツールには適用しない。

## 窓口には「もらう」と「渡す」がある

- **もらう（データを見る）**：スポットを検索する、レビューを読む、保存リストを見る
- **渡す（データを作る・変える）**：レビューを投稿する、保存する、連携を解除する

「見るだけ」なのか「何かを変える」のか。この違いだけ意識すれば十分。

---

## 窓口にもドメインのルールが効く

窓口は「なんでも通す」わけではない。**ルール違反の注文は断る。**
この「断る条件」が、ドメインで決めたルールそのもの。

| 窓口 | 断る条件 |
| --- | --- |
| レビューを投稿する | 評価が未選択なら断る |
| レビューを編集・削除する | 書いた本人でなければ断る |
| 共有で保存する | パートナーと連携していなければ断る |
| サプライズを共有に変える | 連携していなければ断る |
| 共有をサプライズに戻す | **窓口自体を作らない**（一度見られた可能性は消せない） |
| 招待コードを発行する | 既に連携していれば断る／短時間に繰り返せば断る |
| 招待コードを入力する | 期限切れ・使用済み・自分のコード・発行者が既に連携済みなら断る |
| 連携を解除する | 連携していなければ断る |
| 通報する | 自分の投稿なら断る／二重なら断る |
| 退会する | レビューの扱いを選んでいなければ断る |

### 断り方にもルールがある

**招待コードだけは、断る理由を伝えない。**

期限切れでも使用済みでも存在しなくても、返すのは同じ「このコードは使用できません」。
理由を区別すると、**コードが存在するかどうかを外部から判定できてしまう**ため。

他の窓口では、何が悪かったかを具体的に伝える。ここだけが例外。

## 設計上の判断

### 1. スポット詳細は2回に分ける

「スポット情報」と「レビュー一覧」を1つの窓口にまとめない。

理由は、**レビューだけが絞り込みとページングで何度も変わる**から。
1つにまとめると、絞り込みを切り替えるたびにスポット情報まで取り直すことになる。

### 2. 絞り込みは「探す軸」と「自分たち軸」で扱いを変える

ワイヤーフレームで、軸が2種類あることを決めた。窓口でも同じ分け方をする。

| 種類 | 軸 | 送り方 |
| --- | --- | --- |
| 探す軸 | エリア・カテゴリ・シーン | クライアントが明示的に送る |
| 自分たち軸 | ステージ・予算帯・子連れ訪問 | **`personalize=true` を送ると、サーバが会員の情報から補完する** |

**クライアントが自分のステージを組み立てて送らない。**
そうすると「今のステージは何か」の判断がクライアントとサーバの2箇所に存在することになり、ずれる。

ただし「調整する」で今回だけ変えたい場合は、明示的なパラメータが優先される。

### 3. サプライズの秘匿は、窓口の設計で保証する

**画面で隠すのではなく、APIが返さない。**

- `GET /api/v1/saved_spots` は、常に**認証済みの本人の視点**で返す
- `couple_id` を指定させない。パートナーの視点を要求する方法がそもそも存在しない
- `visibility=private` の一覧は、`owner_id` が本人の行だけを返す
- **件数を返すエンドポイントでも、パートナーのサプライズは数に含めない**

`GET /api/v1/spots/{id}` が返す「保存済みかどうか」も、本人の保存だけを見る。
パートナーがサプライズ保存していても、そのフラグは立たない。

これがドメイン設計の「保存されているスポットの表示が、パートナー側で他と変わらない」の実装上の担保になる。

### 4. エラーの形式を統一する

RFC 9457（Problem Details）で統一し、`doc/api/openapi.yaml` に定義する。
Content-Typeは`application/json`ではなく`application/problem+json`を返す（RFC 9457のメディア型）。

```json
{
  "type": "https://couplegifted.example/errors/invitation-code-unusable",
  "title": "このコードは使用できません",
  "status": 422,
  "request_id": "..."
}
```

**招待コードのエラーは、原因が何であってもこの1種類だけを返す。**

### 5. 一覧はカーソルページネーション

ページ番号ではなくカーソルを使う。
新しいレビューが投稿されると、ページ番号方式では並びがずれて重複や取りこぼしが起きるため。

### 6. 契約の維持

- `doc/api/openapi.yaml` をSSoTとする
- Rails側は committee-rails でリクエスト／レスポンスを検証（`backend/spec/rails_helper.rb`で設定）
- Next.js側は openapi-typescript で型を生成する。**手書きの型をフロントに置かない**（未導入）
- CIでスキーマと実装のドリフトを検知し、外れたら落とす（未整備）

## この工程で判明した論点

| # | 論点 | 内容 |
| --- | --- | --- |
| 1 | `GET /me` に何を含めるか | 連携状態・ステージ・パートナーのステージ（食い違い判定用）まで含めると重くなる。分けるか一括か |
| 2 | ランキングのキャッシュ | 集計結果を毎回計算するか、日次で作り置きするか |
| 3 | 写真のアップロード経路 | APIを経由するか、署名付きURLで直接ストレージに送るか |
| 4 | 退会時のレビューの扱いをどう渡すか | `DELETE /me` のリクエストボディで選択を受け取る想定だが、DELETEにボディを持たせる是非がある |

## ポイント

- APIは「注文の窓口」。画面は中の仕組みを知らなくても、窓口に頼めば結果が返る
- 窓口の一覧は、ドメインの動詞から作れる。新しく考えることはほとんどない
- 窓口には「もらう」と「渡す」がある
- 窓口も、ドメインのルールに従って**ルール違反の注文は断る**
- **断り方にもルールがある。** 招待コードだけは理由を伝えない
- **見せない情報は、画面で隠すのではなく窓口が返さない**
- 細かいURLの付け方はAIに作らせていい。ただし**「どんな窓口が必要か」「なぜこの窓口か」は自分で説明できること**
