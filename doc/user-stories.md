# ユーザーストーリー

- **最終更新**：2026-07-30
- **前提ドキュメント**：`doc/requirements.md`
- **本書の目的**：要件定義書で定義した機能が「誰の・どんな目的のためか」を言語化し、実装とテストの起点にする

---

## ユーザーストーリーとは

**誰が・何をしたいか・なぜか**を短い文章で表したもの。

```bash
「〇〇として、△△したい、なぜなら□□だから」
```

| 要素 | 意味 | 例 |
| --- | --- | --- |
| 〇〇として | 誰が使うか（役割） | 会員として、管理者として |
| △△したい | 何をしたいか（行動） | 関係ステージを更新したい |
| なぜなら□□だから | なぜ必要か（目的・理由） | 状況に合った提案を受けたいから |

### 要件定義との違い

| | 要件定義 | ユーザーストーリー |
| --- | --- | --- |
| 視点 | システム視点（何ができるか） | ユーザー視点（なぜ必要か） |
| 例 | 保存リストに可視性を持たせる | 会員として、パートナーに見えない保存リストを作りたい。なぜならサプライズを準備したいから |
| 役割 | 機能の定義 | 機能の目的の言語化 |

### 本プロジェクトでの使い方

ユーザーストーリーは受け入れ条件に展開し、そのまま自動テストのケースにする。
**受け入れ条件を書けないストーリーは、まだ要件が固まっていないものとして扱う。**

## STEP1. アクターの定義

| アクター | 説明 |
| --- | --- |
| ゲスト | 未登録・未ログインの訪問者 |
| 会員（ソロ） | 登録済みだが、パートナーと連携していない |
| カップルメンバー | パートナーと連携済みの会員 |
| 管理者 | サービスを運営・管理する人 |

### アクター設計の判断

- **「会員（ソロ）」と「カップルメンバー」を分けた。** 本サービスは連携の有無で使える機能が変わる。同じ「会員」として扱うと、権限と体験の差が設計から抜け落ちる
- **「パートナー」は独立したアクターにしない。** パートナーは役割ではなく関係であり、常に会員またはカップルメンバーのいずれかである。ただし「パートナーに見せない」という要求は多数のストーリーに現れるため、STEP3で受け入れ条件として明示する
- **「カップル」自体は主語にしない。** 記録の単位はカップルだが、意思を持って操作するのは常に個人である

## STEP2. ユーザーストーリーの洗い出し

優先度は要件定義書の区分に対応する。【M】= Must、【S】= Should、【C】= Could。
末尾に「※」があるものは、要件定義書の未決事項に依存する。

### ゲストのユーザーストーリー

- 【M】ゲストとして、新規登録したい。なぜなら自分のアカウントを作成してサービスを利用したいから
- 【M】ゲストとして、ログインしたい。なぜなら自分のアカウントにアクセスしてサービスを使いたいから
- 【M】ゲストとして、登録せずにスポットを検索・閲覧したい。なぜなら登録する価値があるサービスかを先に確かめたいから

### 会員（ソロ）のユーザーストーリー

**認証・アカウント***

- 【M】会員として、ログアウトしたい。なぜなら共用の端末でも安全に使いたいから
- 【M】会員として、退会したい。なぜなら使わなくなったときに自分の情報を残したくないから
- 【M】会員として、退会時に自分が書いた記録を残すか消すかを選びたい。なぜなら消したいものと残したいものが違うから ※
- 【M】会員として、自分の情報の開示や削除を請求したい。なぜなら自分の情報が何に使われているかを知る権利があるから

**プロフィール***

- 【M】会員として、ニックネーム・年代・居住エリア・好みのタグを編集したい。なぜなら自分に合った提案を受けたいから
- 【M】会員として、子どもの有無を登録したい。なぜなら子連れで出かけるときの選択肢を初期値として絞り込みたいから

**カップル連携***

- 【M】会員として、パートナーと連携しないまま使い始めたい。なぜなら相手を巻き込む前に自分だけで試したいから
- 【M】会員として、招待コードを発行してパートナーを誘いたい。なぜならパートナーと連携して記録を残したいから
- 【M】会員として、受け取った招待コードを入力して連携したい。なぜなら自分の意思で関係を成立させたいから
- 【M】会員として、発行した招待コードがまだ有効かどうかを確認したい。なぜなら渡し損ねたのか、相手が迷っているだけなのかを判断したいから
- 【M】会員として、受け取った招待コードを使わないという選択をしたい。なぜならまだ連携する気持ちになっていないから
  - この要求は「何もしないこと」で満たされる。拒否操作は設けない（後述）
- 【M】会員として、招待コードを再発行したい。なぜなら渡す前に紛失したり、期限が切れたりするから

**スポットを探す***

- 【M】会員として、エリア・カテゴリ・予算帯・シーンでスポットを絞り込みたい。なぜなら条件に合う候補だけを見たいから
- 【M】会員として、スポットの詳細と評価を見たい。なぜなら行くかどうかを判断したいから
- 【M】会員として、ランキングを見たい。なぜなら何から見ればいいかわからないときの入り口が欲しいから

**記録***

- 【M】会員として、一人でもスポットの記録を残したい。なぜなら連携する前から記録を貯めておきたいから

**保存***

- 【M】会員として、パートナーに見えない形でスポットを保存したい。なぜなら連携前でもサプライズの準備をしたいから

**安全***

- 【M】会員として、不適切な投稿を通報したい。なぜなら不快な内容を見せられたまま我慢したくないから

### カップルメンバーのユーザーストーリー

**関係ステージ***

- 【M】カップルメンバーとして、交際開始日や結婚日を登録したい。なぜなら自分たちの状況に合った提案を受けたいから
- 【M】カップルメンバーとして、関係ステージが変わったら更新したい。なぜなら同棲・結婚・出産で行きたい場所の基準が変わるから

**記録（レビュー）***

- 【M】カップルメンバーとして、二人で行った体験として記録を残したい。なぜなら個人の感想ではなく二人の記録として残したいから
- 【M】カップルメンバーとして、評価と一緒に予算帯・シーン・子連れ訪問を記録したい。なぜなら後から同じ条件で探し直したいから
- 【M】カップルメンバーとして、パートナーの反応を記録したい。なぜなら次に何を選べば喜ばれるかの手がかりにしたいから
- 【M】カップルメンバーとして、記録したときの関係ステージがそのまま残ってほしい。なぜならその評価が「いつの自分たちの評価か」を後から読み取れるようにしたいから
- 【M】カップルメンバーとして、書きかけの記録をパートナーに見せずに保存したい。なぜならまとまっていない状態を見られたくないから
- 【M】カップルメンバーとして、自分の記録を編集・削除したい。なぜなら間違いや気が変わったことを直したいから

**記録を読む***

- 【M】カップルメンバーとして、自分たちに近い関係ステージの人の記録だけを読みたい。なぜなら状況が違う人の評価は参考にならないから
- 【M】カップルメンバーとして、自分たちに近い予算帯（ふたり合計）の記録だけを読みたい。なぜなら払える範囲での満足度を知りたいから
- 【M】カップルメンバーとして、子連れ訪問の条件が近い記録を読みたい。なぜなら子どもを連れて行ったかどうかで評価が大きく変わるから
- 【M】カップルメンバーとして、関係ステージ別のランキングを見たい。なぜなら同じ状況の人が良いと言った場所を知りたいから

**保存リスト***

- 【M】カップルメンバーとして、二人で共有する候補リストを作りたい。なぜなら次にどこへ行くかを一緒に決めたいから
- 【M】カップルメンバーとして、パートナーには絶対に見えない保存リストを作りたい。なぜならサプライズを準備したいから
- 【M】カップルメンバーとして、サプライズの保存リストが誤ってパートナーに見えないと確信したい。なぜなら一度でも漏れたらこの機能を二度と使えないから

**提案を受ける***

- 【M】カップルメンバーとして、いくつかの質問に答えるだけで提案を受けたい。なぜなら自分で探す負荷を減らしたいから

**振り返る***

- 【S】カップルメンバーとして、過去に行った場所を見返したい。なぜなら記念日に二人で思い出を振り返りたいから
- 【S】カップルメンバーとして、行った記録を先に残して、レビューは後で書きたい。なぜならその場で長い文章を書く余裕はないから
- 【S】カップルメンバーとして、記念日を登録して知らせてほしい。なぜなら準備が間に合わないまま当日を迎えたくないから

**関係の終了***

- 【M】カップルメンバーとして、パートナーとの連携を解除したい。なぜなら関係が終わった相手と記録を持ち続けたくないから
- 【M】カップルメンバーとして、連携解除するときにカップルレビューと共有保存リストの扱いを選びたい。なぜなら見たくない記録と残しておきたい記録があるから ※
- 【M】カップルメンバーとして、解除したことが相手に通知されるかどうかを事前に知りたい。なぜなら通知されるかどうかで解除するタイミングを選びたいから ※

### 管理者のユーザーストーリー

- 【M】管理者として、スポットを登録・編集したい。なぜなら掲載情報の正しさを運営として担保したいから
- 【M】管理者として、届いた通報を一覧で確認したい。なぜなら対応漏れを起こしたくないから
- 【M】管理者として、不適切な投稿を削除したい。なぜなら安全に使える場を維持したいから
- 【M】管理者として、規約違反のユーザーを停止したい。なぜなら繰り返される加害を止めたいから
- 【M】管理者として、自分が行った削除や停止の記録を残したい。なぜなら誰がいつ何をしたかを後から説明できるようにしたいから
- 【S】管理者として、通報から対応までにかかった時間を把握したい。なぜなら対応の遅れに気づけるようにしたいから

## STEP3. 受け入れ条件

> すべてのストーリーには最終的に受け入れ条件を付けるが、ここでは**解釈が分かれるもの・実装を誤ると信頼を失うもの**を先に定義する。

### サプライズ保存リストはパートナーに見えない

対象ストーリー：「パートナーには絶対に見えない保存リストを作りたい」

- 保存時に「共有」か「サプライズ」を選択できる
- サプライズとして保存したものは、パートナーのアカウントからは一覧・詳細・検索結果・件数のいずれにも現れない
- 「サプライズの保存が存在すること自体」もパートナーに伝わらない
- 保存の対象になっているスポットの表示が、パートナー側で他と変わって見えない
- サプライズから共有への変更はできるが、変更した時点でパートナーに見えるようになることを事前に警告する
- 通知・メールなど、アプリ外の経路でも漏れない

### 記録した時点の関係ステージが保持される

対象ストーリー：「記録したときの関係ステージがそのまま残ってほしい」

- 記録の投稿時、そのカップルの当時の関係ステージが記録に紐づけられる
- 後で関係ステージを更新しても、過去の記録に紐づいたステージは変わらない
- 交際開始日や結婚日を訂正した場合も、過去の記録のステージは変わらない
- 記録の表示時、そのステージが「投稿当時のもの」であることが読み手に伝わる
- ステージ別ランキングの集計は、投稿当時のステージを基準にする

### 連携解除

対象ストーリー：「パートナーとの連携を解除したい」

- 片方の意思のみで解除できる（相手の承認を必要としない）
- 連携解除の実行前に、カップルレビューと共有保存リストがどうなるかが提示される
- 解除後、相手のサプライズ保存リストが自分に見えるようになることはない
- 解除後、同じ相手と再度連携できる
- 解除は取り消せないため、実行前に確認を求める
- ※ 連携解除後のカップルレビューと共有保存リストの帰属、相手への通知の有無は要件定義書の未決事項

### 招待コードの有効期限と状態表示

対象ストーリー：「招待コードがまだ有効かどうかを確認したい」「招待コードを使わないという選択をしたい」

**方式***

- 招待はコード方式とする。相手を指定して送るのではなく、コードを発行して利用者自身が任意の手段（LINE等）で渡す
- したがって受け取る側に「届いた招待」という状態は存在せず、**拒否操作は設けない**
- コードを入力しなければ、期限切れによって自然に無効になる

**コードの有効性***

- 有効な招待コードは、1アカウントにつき常に1つだけ存在する
- 再発行した時点で、それ以前のコードは即座に無効になる
- コードは1回の連携成立で使い切りとなる
- 有効期限は発行から7日間
- コードは推測が困難な長さと文字種を持つ。読み違いを避けるため `0` `O` `1` `I` `l` は使用しない

**発行側への見せ方***

- 発行側は、自分のコードが有効かどうかと残り日数を画面上で確認できる
- 状態の変化（未使用のまま期限切れ、連携成立）を**通知・メールで送らない**
- 表示の文言は相手の不作為を指さない。「相手がまだ使っていない」ではなく「有効（残り5日）」のように、コードの状態として表現する

**濫用の防止***

- 招待コードの入力に連続して失敗した場合、そのアカウントからの入力を一時的に制限する
- コードの発行にもレート制限を設ける。正当な利用を妨げない水準とする
- 制限に達した場合、いつ再試行できるかを利用者に提示する

## 補足：本サービス特有の設計上の注意

### ネガティブなストーリーを意図的に含めた

解除する・通報する・退会する。実運用では必ず発生し、かつ**設計から漏れると取り返しがつかない**行動である。
特に関係の終了は、恋愛・結婚を扱うサービスにおいて例外ではなく通常の分岐として扱う。

なお「招待を断る」は、当初ストーリーとして立てていたが削除した。
招待をコード方式にした結果、断るという操作が不要になったためである（受け入れ条件の章を参照）。
**ネガティブな行動は、機能で受け止めるより、そもそも操作を必要としない設計にできるならその方が良い。**

### 「絶対に見えない」を受け入れ条件に落とし込む必要がある

サプライズ機能は、一度でも漏れれば機能そのものが使われなくなる。
「見えないこと」は通常の正常系テストでは検証できないため、**見えないことを確認するテスト**を明示的に用意する。

### 未決事項に依存するストーリーには「※」を付けた

要件が固まっていないストーリーを実装に流さないための印。
※ が付いたストーリーは、要件定義書の未決事項が解消されるまで着手しない。
