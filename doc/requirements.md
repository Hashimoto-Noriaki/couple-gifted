# CoupleGifted 要件定義書

> 交際中から結婚後までのふたり向けライフプラットフォーム。「パートナーが喜ぶ」を軸に、交際を始めたばかりの頃から結婚後まで長く使えるサービス。

- **最終更新**：2026-07-31
- **ステータス**：ドラフト
- **本書の範囲**：何を作るか（要件）のみを定義する。どう作るか（ドメイン・画面・DB・API）は別ドキュメントで定義する

## 00. このプロジェクトの目的

**実際に運用するサービスとして開発する。** 動けばよいデモではなく、ユーザーを迎えて継続的に運用できる状態をゴールとする。

そのため、以下を「後回しにしない」前提で設計する。

- 個人情報の適切な取り扱いと、法令に基づく開示・削除への対応
- 不適切な投稿への対処手段
- 障害の検知・復旧・データのバックアップ
- 機能追加とデータ移行を継続的に行える構造

副次的に、本プロジェクトの設計判断と開発プロセスは職務経歴書・スキルシートの裏付けとしても用いる。ただし**設計判断はポートフォリオ映えではなく運用上の必要性を基準に行う**。過剰な技術選定は減点とみなす。

## 01. ユーザーインタビュー

> 実際の利用者に「困りごと」や「ゴール」を聞く。机上で機能を考える前に、リアルな課題を把握する。

- **インタビュー対象**：交際を始めたばかりのふたりから、結婚10年目のふたりまで（20〜40代）。関係ステージを意図的に広く取った
- **主な質問例**
  - デートの行き先はどうやって決めていますか？
  - 過去に行って良かった場所を覚えていますか。記録していますか？
  - 関係が変わって（同棲・結婚・出産）、行きたい場所の基準は変わりましたか？
  - パートナーに隠して準備したことはありますか？
- **インタビューで得られた主な声**

| 関係ステージ | 声 |
| --- | --- |
| 交際初期 | 「最初のうちは店選びを外したくない。緊張する」 |
| 交際初期 | 「相手の好みがまだわからないので、無難な選択に逃げてしまう」 |
| 交際中期 | 「毎回同じ店になる。行き先を決めるのがどちらかの負担になっている」 |
| 交際中期 | 「グルメサイトの評価は参考にならない。“二人で行って良かったか”が知りたい」 |
| 婚約・新婚 | 「両家の顔合わせや記念日など、失敗できない場面が急に増えた」 |
| 夫婦 | 「独身の頃に良かった店が、子どもができてからは使えない」 |
| 夫婦 | 「子どもを預けて二人で出かける日は、選ぶ基準がまったく変わる」 |
| 全般 | 「サプライズを準備したいのに、共有アプリだと相手にバレる」 |
| 全般 | 「良かった場所をLINEに送りっぱなしで、後から探せない」 |

## 02. カスタマージャーニーマップ

> 利用者の行動・感情の流れを可視化し、各接点でのニーズを把握する。

| フェーズ | 行動 | 感情 | ニーズ |
| --- | --- | --- | --- |
| 認知 | サービスの存在を知る | 「行き先探しが楽になるかも」 | 何のサービスか一目でわかる |
| 登録 | 新規登録・プロフィール入力 | 「まずは1人で試したい」 | 相手を巻き込まずに始められる |
| 連携 | 招待コードでパートナーと連携 | 「誘うのが少し照れくさい」 | 誘うのが軽い・使われなくても気まずくならない |
| 探す | スポットを検索・絞り込み | 「自分たちに合う場所が知りたい」 | 関係ステージ・予算・シーンで絞れる |
| 決める | 詳細とレビューを読む | 「実際どうだったのか知りたい」 | 自分たちと近い状況の人のレビューが読める |
| 行く | 訪問する | 「思ったより良かった／微妙だった」 | ー |
| 記録 | レビューを書く | 「面倒」「でも残しておきたい」 | 入力が短時間で終わる |
| 隠す | サプライズを準備する | 「バレたくない」 | 相手に見えない保存リストがある |
| 変化 | 同棲・結婚・出産で状況が変わる | 「前と同じ探し方ができない」 | ステージを更新すると結果も変わる |
| 再訪 | 記念日・節目に見返す | 「あの時ここに行ったな」 | 過去の記録が資産になっている |
| 離脱 | 使わなくなる | 「書くことがない」 | 記録の負荷が低い・見返す動機がある |
| 関係終了 | 別れる・離婚する | 「あの記録を見たくない／残したい」 | 記録の扱いを自分で選べる |

※ 本表は利用者の視点で書くため、利用者に見せる言葉としての「記録」を用いている。ドキュメント上の用語としては「レビュー」に対応する。

## 03. 課題定義

- **誰の課題か**：交際初期から夫婦まで、あらゆる関係ステージのふたり
- **どんな課題か**：行き先の選択が毎回ゼロからのやり直しになり、意思決定の負荷が片方に偏る
- **現状の問題**
  1. 既存のレビューサービスの評価は「個人が」「単独で」の評価であり、二人で行った体験の評価軸がない
  2. 関係ステージによって最適な選択は大きく変わるのに、その軸で絞り込めない
  3. 既存の共有ツールは相手に見せることしかできず、サプライズの準備ができない
  4. 関係ステージが変わったとき、過去のレビューとの連続性が失われる

### 関係ステージの定義

本サービスの中核となる区分。全ステージを対象とする。

| ステージ | 定義 | 想定される主なニーズ |
| --- | --- | --- |
| 交際初期 | 交際開始から6ヶ月未満 | 失敗しない・相手の好みを探る |
| 交際中期 | 交際6ヶ月以上 | マンネリ回避・新しい選択肢 |
| 婚約中 | 婚約から結婚まで | 記念日・両家対応・失敗できない場面 |
| 新婚 | 結婚から1年未満 | 二人の生活の起点作り |
| 夫婦 | 結婚1年以上 | 日常の中の非日常・記念日 |

交際初期と交際中期をまとめて指す場合は「交際期」と呼ぶ。「交際中」は意味が広すぎるためステージ名には用いない。

### 子どもに関する2つの属性

子どもに関する情報は、**性質の異なる2つの属性に分ける**。

| 属性 | 意味 | 用途 |
| --- | --- | --- |
| **子どもの有無** | 子どもがいるかどうか | プロフィールに保持し、検索条件の初期値を補完する |
| **子連れ訪問** | そのとき子どもを連れて行ったか | レビューの属性・検索の絞り込み軸 |

**子どもがいる夫婦が、子どもを預けて二人で出かけることは頻繁にある。** 絞り込みに必要なのは「子連れ訪問」であり、「子どもの有無」ではない。関係ステージには子どもに関する情報を含めない。

## 04. 解決策の定義

- **何を作るか**：関係ステージ軸でパーソナライズされる、ふたり向けデートスポットのレビューサービス
- **どう解決するか**
  1. レビューに「関係ステージ・予算帯・シーン・子連れ訪問」を属性として持たせる
  2. 閲覧側は自分たちの状況に近いレビューだけを見られる
  3. 保存リストに可視性を持たせ、パートナーに見えないサプライズを可能にする
  4. ステージが変わっても、過去のレビューは投稿当時のステージのまま保持される
- **スコープ外（やらないこと）**
  - プレゼント／コスメのドメイン（構想には含むが本フェーズでは実装しない）
  - 決済・課金
  - リアルタイムチャット
  - SNS的なフォロー／タイムライン
  - LLMを使ったレコメンド（診断はルールベースで実装する）
  - ネイティブアプリ

### スコープに関する判断

構想上の CoupleGifted は「デートスポット・プレゼント・コスメ」の3ドメインを扱う。
しかしこの3つは本来別サービスであり、同時提供は「一言で説明できないサービス」を生む。

**第1フェーズではデートスポットのみを提供する。** 他ドメインは同一の構造で拡張可能な設計とするが、実装はしない。

## 05. 成功指標

> 網羅的なKPI表は作らない。**検証したい仮説を1つに絞り、それが外れていないかを測る**ことだけを目的とする。

### 検証したい仮説

**「関係ステージで絞り込めると、行き先の意思決定が楽になる」***

これは本サービスの存在理由そのものである。この仮説が外れている場合、他のどの指標が良くても方向転換が必要になる。

### 測る指標

| 指標 | 何を判断するか |
| --- | --- |
| ステージによる絞り込みの使用率 | 仮説の直接検証。使われないなら価値の中心が別にある |
| 絞り込みを使った場合と使わなかった場合で、保存に至る率に差があるか | 絞り込みが実際に意思決定を助けているか |
| 登録者のうちカップル連携に至った割合 | 連携が導入の壁になっていないか（失敗の早期検知） |
| 2件目のレビューを投稿した人の割合 | 記録の負荷が許容範囲か（失敗の早期検知） |

上2つが本命。下2つは、仮説が正しくても別の理由で失敗している状態を早く見つけるために置く。

計測は各機能の実装と同時に仕込む。リリース直前にまとめて入れると全画面を触り直すことになる。

### 測らないもの

DAU・MAU・滞在時間などの一般的な指標は、この規模では有意な差が出ず判断に使えないため追わない。

## 07. 機能要件

### Must（第1フェーズ／リリース必須）

**アカウント***

- 新規登録・ログイン・ログアウト
- プロフィール編集（ニックネーム・年代・居住エリア・好みタグ・子どもの有無）
- 退会（データの取り扱いを利用者が選択できる）

**カップル***

- 招待コードの発行・入力による連携。ソロ状態でも利用開始できる
  - 有効なコードは1アカウントにつき常に1つ。再発行時に旧コードを無効化する
  - 有効期限は7日。連携成立で使い切り
  - 拒否操作は設けない。使われなければ期限切れで自然に終了する
  - コードの状態は発行側の画面で確認できるが、状態変化を通知しない
- 関係ステージの設定。**交際初期・交際中期・婚約中・新婚・夫婦から本人が選ぶ**（日付は収集しない）
- 記念日の任意登録（複数可）。意味は本人が決める。ステージ判定には使わない
- 連携解除。解除時、カップルレビューと共有保存リストの扱いを利用者が選択できる

**スポット***

- エリア・カテゴリ・予算帯・シーンでの検索と絞り込み
- 詳細表示（基本情報・評価サマリ・レビュー一覧）
- ステージ別・エリア別ランキング

**レビュー***

- 投稿（5段階評価／関係ステージ／予算帯／シーン／子連れ訪問／パートナーの反応／本文／写真）
- **予算帯はふたり合計・税込**とする。画面上に必ず単位を明示する
- 投稿時点の関係ステージを保持する（後からステージが変わっても書き換わらない）
- 属性による絞り込み閲覧（自分たちに近い状況のレビューのみ表示）
- 編集・削除

**保存リスト***

- 共有モード（パートナーにも見える）
- サプライズモード（本人のみ）

**診断***

- 数問の質問への回答からスポットを提示する（ルールベース）

**運営***

- 投稿の通報
- 管理者による通報対応・投稿削除・ユーザー停止
- スポットマスタの登録・編集

### Should（第1フェーズ内で時間が許せば）

- 訪問記録とレビューの紐付け（行った → 後で書く）
- 記念日の登録とリマインド
- レビューへの「参考になった」

### Could（第2フェーズ以降）

- プレゼント／コスメドメインへの拡張
- 通知（メール／プッシュ）
- LLMを用いたレコメンド

## 08. 運用要件

> 実運用を前提とするため、機能要件と同格で定義する。

### 個人情報の取り扱い

- **交際開始日・婚約日・結婚日は収集しない。** ステージ判定に不要であり、本人にとって重い情報になり得るため
- 関係ステージ・記念日・パートナーとの関係は、本人の同意なく第三者に開示されない情報として扱う
- 利用規約・プライバシーポリシーをリリース時点で用意する
- 開示・訂正・削除の請求に対応できる手段を持つ
- 収集する情報は、機能の実現に必要な最小限に限る

### 退会とデータ削除

以下は**リリース前に必ず決定する**。未決のままリリースしない。

| ケース | 決定事項 | 状態 |
| --- | --- | --- |
| 会員が退会したとき、ソロレビュー | 匿名化して残すか、削除するか | 未決 |
| 会員が退会したとき、カップルレビュー | 相手側にどう見えるか | 未決 |
| 会員が退会したとき、共有保存リスト | 相手に残すか | 未決 |
| 一定期間ログインがない場合 | 休眠・削除の方針 | 未決 |

### 連携解除時のデータ

関係の終了は日常的に発生する。**運用上もっともクレームになりやすい箇所**として、要件を先に固める。

| 項目 | 方針 | 状態 |
| --- | --- | --- |
| 解除後、カップルレビューの所有 | 執筆者側に帰属させる想定 | 要検討 |
| 解除後、相手が書いたレビューの閲覧可否 | 公開済みのものは閲覧可の想定 | 要検討 |
| 解除後、共有保存リスト | 双方に複製するか、片方に帰属させるか | 未決 |
| 解除の相互合意要否 | 片方の意思のみで解除可能とする想定 | 要検討 |
| 解除の相手への通知 | 通知するか否か | 未決 |

### スポットマスタの調達

**リリース前に必ず決定する。** 実運用では架空データを使えない。

| 選択肢 | 論点 |
| --- | --- |
| 外部APIの利用 | 利用規約上のキャッシュ・再配布制限、従量課金、サービス継続リスク |
| 運営による手動登録 | 初期データ量の確保、更新コスト |
| ユーザー投稿 | 重複・品質・スパム対策、モデレーション負荷 |

### モデレーション

- 通報を受け付ける手段を提供する
- 通報から対応までの一次対応時間の目安を定める
- 対応履歴を記録する

### 運用体制

- 稼働監視とエラー通知を行う
- データベースのバックアップを日次で取得し、復旧手順を検証済みにしておく
- 障害発生時の利用者への告知手段を持つ

## 09. 非機能要件

### 前提とする規模

要件の水準は以下の想定に基づく。規模が変わった場合は要件も見直す。

- 初年度の登録者数：数百人規模
- 同時アクセス：ピーク時で数十
- スポットマスタ：数千件
- レビュー：年間数千件

この規模では、検索・集計はPostgreSQLの標準機能で成立する。専用の検索基盤や分散構成は導入しない。

### 要件

| 項目 | 要件 |
| --- | --- |
| パフォーマンス | 主要画面の初期表示が3秒以内。一覧・検索は件数が増えても劣化しないこと |
| 可用性 | 計画外の停止時、利用者に状況を伝えられること。データを失わないこと |
| データ整合性 | 評価の集計値が実データと乖離しないこと。乖離を検知できること |
| セキュリティ | 認証情報を平文で保持しない。SQLインジェクション・XSS・CSRFへの対策を行う。認可の判定を一箇所に集約し、画面ごとの実装差異を生まない |
| サプライズの秘匿 | サプライズ保存リストは、一覧・詳細・検索結果・件数のいずれにもパートナー側に現れないこと。**見えないことを検証するテストを持つこと** |
| 招待コードの保護 | 招待コードは他人のカップルへ侵入する鍵となるため、推測が困難であること。入力の連続失敗に対して制限をかけ、総当たりを成立させないこと |
| 監査性 | 削除・停止などの管理操作の実行者と日時を記録する |
| API契約 | APIの仕様を唯一の正とし、実装との乖離を自動で検知できること |
| テスト | 主要な機能に自動テストを持ち、変更時に回帰を検知できること。テストは1コマンドで完走すること |
| 変更容易性 | スキーマ変更を安全に適用でき、危険な変更を事前に検知できること |
| 可観測性 | 障害発生時に、利用者から受けた報告と実際のログを突合できること |
| コード品質 | 静的解析を自動で強制し、レビューで指摘しなくても品質が保たれること |

## 11. 開発プロセス

- **APIファースト**：APIスキーマを先に定義し、両端の実装をそれに従わせる。ただし全エンドポイントを実装前に書き切るのではなく、機能ごとにスキーマ先行とする
- **TDD**：Red → Green → Refactor でコミットを刻む
- **AI駆動開発のハーネス**：設計方針と禁止事項を `docs/design-principles.md` に明文化し、`CLAUDE.md` を薄い入口として置く。決定的なseedを用意し、人間・AIのどちらが触っても同じ結果が再現できる状態を保つ
- **意図的な設計判断の保護**：非正規化など「一見おかしいが意図的」な箇所は、コード上にも理由を残す。設計判断を変更する前に決定事項ログを確認する

## 12. スケジュール

実運用構成のため、リリースと運用開始を分けて計画する。

### 第1フェーズ：MVPリリースまで（3ヶ月）

**レイヤーではなく機能で縦に切る。各週の終わりに、常にデプロイ済みで動いている状態を保つ。**

| 期間 | 内容 | 週末の状態 |
| --- | --- | --- |
| Week 1 | 未決事項 #1・#4・#6・#7・#11 の決定 → ドメイン設計 → 画面遷移図 | 構造が決まっている |
| Week 2 | ワイヤーフレーム・デザイン方針・ER図/DB設計・環境構築（Docker/CI）・ハーネス整備 | CIが動き、空の本番環境が公開されている |
| Week 3-4 | 縦串の貫通。スポット検索と詳細を、本番と同じ構成（Rails・PostgreSQL・Next.js）のまま一本通してデプロイする | **人に見せられる。スポットを検索して見られる** |
| Week 5 | 認証・アカウント | ログインできる |
| Week 6 | レビューの投稿・表示 | 記録を残せる |
| Week 7 | カップル連携（コード発行・連携・期限切れ・解除） | 二人で使える |
| Week 8 | 関係ステージと属性による絞り込み | **仮説の中心機能が動く** |
| Week 9 | 保存リストと可視性制御（共有・サプライズ） | サプライズを準備できる |
| Week 10 | 診断とレコメンド | 提案を受けられる |
| Week 11 | 管理機能・通報・モデレーション | 運営できる |
| Week 12 | E2E・パフォーマンス計測・利用規約整備 | リリースできる |

Week 3-4 の縦串貫通を最優先とする。ここが遅れると、API契約の不整合や型生成の問題に気づくのが終盤になり、手戻りが最大化する。

**モックや仮実装は作らない。** Week 3-4 で作るものは本番構成そのものであり、後から差し替えるものではない。Week 5 以降は、この上に機能を1つずつ足していく。

**Week 1-2 は密度が高い。** 遅れた場合は、Week 2 の設計をスポット検索の分だけに絞り、残りは各機能の実装直前に行う。ドメイン設計とER図・DB設計は構造に関わるため先に済ませるが、ワイヤーフレームとAPI設計は機能ごとに分割してよい。

### 第2フェーズ：運用開始後

- スポットマスタの拡充
- 利用状況の計測と改善
- Should / Could 項目の実装

## 13. 決定事項ログ

| # | 決定 | 理由 | 状態 |
| --- | --- | --- | --- |
| 1 | 実運用を前提とする | 運用しないことを前提にした設計は、後から運用可能にできない | 確定 |
| 2 | 第1フェーズのドメインはデートスポットのみ | 3ドメイン同時提供はサービスの説明可能性を失わせる | 確定 |
| 3 | 関係ステージは交際初期から夫婦まで全般を対象とする | ステージごとにニーズが異なることこそが本サービスの価値であり、範囲を狭めると軸が成立しない | 確定 |
| 4 | 子どもに関する情報を「子どもの有無」と「子連れ訪問」に分離する | 子どもがいても子連れで行くとは限らない。絞り込みに必要なのは訪問のしかたであり、人の属性ではない | 確定 |
| 5 | 投稿時点の関係ステージを保持する | ステージが変わっても過去の評価は当時のものとして残るべき | 確定 |
| 6 | ソロ利用可・後からカップル化 | 招待必須だと登録直後に何もできない。連携解除後もソロ状態に戻るため、一時的な状態ではない | 確定 |
| 7 | レコメンドはルールベースで実装 | 精度を比較できる基準がない状態でLLMを入れても評価できない | 確定 |
| 8 | 通報・モデレーションを第1フェーズのMustに含める | 実運用する以上、不可欠 | 確定 |
| 9 | ドメイン・画面・DB・API設計は本書に含めない | 要件と設計を混在させると、要件変更時にどこを直すべきか判断できなくなる | 確定 |
| 10 | 招待はコード方式とする（相手を指定して送らない） | 相手が未登録でも招待できる。カップルの片方が先に登録するのが最も多い導入経路であるため | 確定 |
| 11 | 招待の拒否操作を設けない | 相手は日常的に会う交際相手であり、断った事実を隠す実利がない一方、「断られました」という明示的な通知は関係に持ち込まれる火種になる。使わなければ期限切れで終わる設計にすることで、断るための操作自体を不要にした | 確定 |
| 12 | 招待コードの状態は表示するが通知しない | 表示は発行側の判断に必要だが、通知はアプリが催促の起点になることを意味する | 確定 |
| 13 | 有効な招待コードは常に1つのみ | 過去に渡したコードが後から使われ、意図しない相手と連携する事故を防ぐ | 確定 |
| 14 | スケジュールをレイヤーではなく機能で縦に切る | レイヤーで切ると終盤まで動くものが存在せず、契約の不整合に気づくのが遅れる | 確定 |
| 15 | 網羅的なKPIを追わず、仮説1つに絞って測る | この規模では一般的な指標に有意差が出ず、判断に使えない | 確定 |
| 16 | リスク一覧・コスト見積もりを独立した章として作らない | 様式の重さが目的を上回る。必要な論点は運用要件と未決事項で管理する | 確定 |
| 17 | 用語を `docs/ubiquitous-language.md` に統一する | 「共有」が可視性・帰属・連携の3つの意味で使われており、そのままでは設計に落とせなかった | 確定 |
| 18 | 予算帯はふたり合計・税込とする | 記録の単位が「二人で行った体験」であるため。既存サービスは一人あたり表示が多いので、画面上に単位を明示する | 確定 |
| 19 | ステージ名に「交際中」を使わない | 「交際初期」も日本語としては交際中であり、並列に置くと判別できない。傘となる語は「交際期」とする | 確定 |
| 20 | 用語集とADRは一括置換の対象外とする | どちらも「当時の言葉」「使わないと決めた言葉」を保持する文書であり、置換すると内容が壊れる | 確定 |
| 21 | APIファーストを「機能ごとにスキーマ先行」と定義する | 全エンドポイントを実装前に書き切ると、縦串の貫通が遅れて契約の不整合の発見が遅れる | 確定 |
| 22 | 指標の計測は各機能の実装と同時に仕込む | リリース直前にまとめて入れると全画面を触り直すことになる | 確定 |
| 23 | 第1フェーズから Rails をバックエンドとして採用する（Next.js 先行での実装は採用しない） | 後からRailsへ移す動機は運用上の痛みを伴わないため実行されにくく、実行しても中身は全面的な書き直しになる。証明したい技術がリリース時点の成果物に現れない点も目的と矛盾する。なお、HTTPの境界を保つ限り、特定機能を後から別言語のサービスとして切り出す道は Rails でも残る | 確定 |
| 24 | 関係ステージは本人が直接選ぶ。交際開始日・婚約日・結婚日を収集しない | ステージ判定に日付は不要であり、日付は本人にとって重い情報になり得る。日付が必要なのは記念日リマインドという付加機能だけなので、任意登録の記念日で受け止める。付加機能のために全員から日付を集めることは「収集する情報は最小限に」と矛盾する | 確定 |
| 25 | 関係ステージは会員が持つ（カップルではなく） | カップルが持つとソロの会員がステージを持てず、レビューが絞り込みとランキングに載らない。連携解除後もソロ状態は続くため、影響期間が長い | 確定 |
| 26 | スポットマスタは運営の手動登録とし、開始エリアを1〜2箇所に絞る | この規模なら100件程度で成立する。外部APIは規約上の保持制限・従量課金・提供終了リスクを一度に持ち込み、見返りが小さい。ユーザー投稿はモデレーション対象が2種類になる | 確定 |
| 27 | 同一スポットへの複数回のレビュー投稿を許す。ただし平均評価の集計は1組1スポットあたり最新の1件のみ | 再訪して評価が変わることは正常であり、同じ組がステージ違いで評価したデータは仮説検証の最良の材料になる。集計対象を絞れば平均の偏りは生じない | 確定 |
| 28 | サプライズ保存と共有保存に同じスポットが同時に存在してよい | 禁止すると共有側から先に外す必要が生じ、その削除がパートナーに見えてしまう。サプライズを守るための制約がサプライズを壊す。警告は本人の画面にのみ出す | 確定 |
| 29 | 公開しないレビューは第1フェーズでは許さない | 立ち上げ期に非公開を選べると、公開レビューという価値の源泉が枯れる。記録欲求は下書きで受け止める。後から公開範囲を足しても壊れない変更である | 確定 |
